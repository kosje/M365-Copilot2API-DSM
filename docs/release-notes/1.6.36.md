### v1.6.36 — 对外链接：支持 Forwarded 头，并说明链接是怎么推导出来的

**背景**：上一版修掉了「转发主机名不带端口」的情况，但你的客户端链接仍然没有端口。对比你给的两张截图后定位到一件事——**web 控制台那条链接从来不能证明推导是对的**：

- 控制台的聊天请求是服务内部转发的，构造时用的是占位主机名 `example.com`，它会被判定为占位域名并拒绝，于是服务端返回的是**相对路径** `/v1/images/files/xxx`。
- 浏览器把这个相对路径拼到页面 origin 上，**端口是浏览器补的**。所以控制台无论推导对不对，看起来都是对的。
- 客户端是第一个真正走「绝对地址」这条路的调用方——**它的请求头才决定结果**，而这我在这边看不到。

**这一版做了两件事**：

1. **支持 RFC 7239 `Forwarded` 头**（`Forwarded: for=1.2.3.4;host=host:52325;proto=https`）。此前只认 `X-Forwarded-Host` / `-Proto` / `-Port`，如果代理只发 `Forwarded`，公网端口就无从得知。现在两种都支持，带引号的值也认，多段列表从左往右取第一个带该字段的；如果一个候选带了端口、另一个没带，优先用带端口的那个。
2. **把推导过程写进日志**（每种情况每次启动只打一次，不刷屏）。当推导不出绝对地址、或推导出的地址不带端口时，会打出用了哪个来源和原始请求头：

```
[public-url] absolute links use "https://..." which states no port. ...
  source=x-forwarded-host host="..." x-forwarded-host="..." x-forwarded-port="..." x-forwarded-proto="..." forwarded="..." override=""
```

> 「不带端口」既可能是代理真的就跑在默认端口上，也可能是端口在转发中被丢掉——从服务端看不出区别，所以只能把依据写出来。

**立刻可用的做法（不必等这版）**：控制台「高级 → 公网访问地址」填入你的真实对外地址（**务必带上端口**）：

```
https://365apijr.tn:52325
```

它优先级最高，绝对链接立刻按它生成，无需重启。对应环境变量 `M365_PUBLIC_BASE_URL`。

**如果升级后仍然不对**：请把 NAS 日志里 `[public-url]` 开头的那一行发我——它包含网关实际收到的 `host` / `x-forwarded-host` / `x-forwarded-port` / `Forwarded`，据此可以直接判断是代理没发端口，还是我这边还漏了某种头部。

**验证**：`Forwarded` 解析（含带引号、含首段无该字段、含无端口时从 Host 借用）、带端口的候选优先、来源标识、`publicBaseHasPort`，以及那行诊断日志本身的字段名（它就是你要回传的东西）。
