### v1.6.34 — 生图结果直接返回图片本身，不再只是一个链接

**变化**：无论你在哪条路径触发生图——web 端 chat 页面、客户端里显式选择 `gpt-image-2`，还是普通模型上的生图意图被自动识别——**返回结果里都直接带着图片本身**（网关下载并重新编码后的字节，以内联 base64 形式随响应一起返回），而不是只给一个需要客户端再去拉取的链接。

**为什么要改**：此前客户端拿到的是指向网关的 Markdown 链接，客户端必须先回头把图片取回来才能显示。这一步在真实环境里经常失败——链接地址是由 `M365_PUBLIC_BASE_URL` 或请求的转发头推导出来的，一旦经过重写 Host 或丢掉公网端口的反向代理就是错的，用户看到的就只剩一个链接。web 端 chat 页面没有这个问题，因为它是同源渲染 `/api/chatui/file/<id>`——这也正是"手动选画图正常、客户端不正常"的原因。

**保留不变**：图片仍会在网关本地保存一份，响应里同时保留 `[下载图片]` 链接，用于打开原图或全尺寸下载。图片仍会按内容去重、并剥离 C2PA/EXIF 元数据（仅生图路径，不动用户上传图）。

**web 端 chat 页面未改动**：它本来就已是"用户看到图片"，而且把图片字节内联进对话存储会让每条消息体积按图片大小膨胀，没有实际收益。

**需要注意的代价**：内联会让响应体积与图片相当（base64 约为原图 1.37 倍）。生图通常 1–3 MB；接受的单图上限是 20 MB，那种情况会得到约 27 MB 的响应体。如果你遇到客户端因此卡住，加一个大小阈值即可（位置在 `chatImageBlocks`）。

**验证**：内联字节与网关托管副本必须解码一致；生产渲染函数分别经 OpenAI 与 Anthropic 两条写出路径验证，且远端 URL 不会出现在图片位置上；alt 文本无法注入第二张图片、链接目标或换行。
